# Deploying the public demo on Render

This guide deploys SubCycle as a **public demo with simulated billing** using the repository's [`render.yaml`](../render.yaml)
Blueprint on Render's **free** plans. Nothing here makes the project production-ready for real money; see
[Why this is not a production billing setup](#why-this-is-not-a-production-billing-setup).

Plan terms below come from Render's documentation as read on 2026-10-29. Free-tier terms change, so re-check
<https://render.com/docs/free> before relying on any number.

## What the Blueprint creates

| Resource | Type | Notes |
|---|---|---|
| `subcycle-db` | PostgreSQL, `free`, PostgreSQL 16, region `oregon` | One free database per Render workspace. |
| `subcycle-api` | Web Service, Node, `free`, region `oregon` | Express API. Health check `/health`. |
| `subcycle-web` | Static Site | Vite build from `client/dist`, with an SPA rewrite and basic security headers. |

Both services use `autoDeployTrigger: "off"`, so a push never redeploys by itself; trigger deploys manually.

### Commands (taken from the workspace scripts)

| Service | Build | Start |
|---|---|---|
| API | `npm ci --include=dev && npm run build -w server` | `npm run db:migrate -w server && npm run db:seed -w server && npm run start -w server` |
| Web | `npm ci --include=dev && npm run build -w client` | none (static) |

- `--include=dev` is required because `NODE_ENV=production` would otherwise skip `tsc`, `vite` and `tsx`.
- `NODE_VERSION=24` matches CI (Render resolves it to the latest 24.x).
- Migrations and seeding run in the **start command** because Render documents the pre-deploy command for paid instances only.
  Both are safe to repeat: migrations are forward-only, checksummed and serialised by an advisory lock; seeding upserts the four
  plans by code. The cost is that every cold start (after a sleep) re-runs them, which is quick when nothing is pending.

## Environment variables

Set by the Blueprint (no action needed): `NODE_VERSION`, `NODE_ENV=production`, `DATABASE_URL` (the database's connection string,
referenced by Render), `JWT_SECRET` (generated by Render), `TRUST_PROXY=1`, `ENABLE_DEV_ENDPOINTS=false`,
`MOCK_BILLING_FAIL=never`, `RUN_JOBS=true`, `JOBS_CRON=* * * * *`.

**You must enter these when the Blueprint is first created** (they are marked `sync: false` because they depend on URLs Render
assigns):

| Variable | Service | Value |
|---|---|---|
| `CORS_ORIGINS` | `subcycle-api` | The exact origin of the web app, for example `https://subcycle-web.onrender.com`. No trailing slash, no wildcard. Production refuses to start without it. |
| `VITE_API_URL` | `subcycle-web` | The API's public URL, for example `https://subcycle-api.onrender.com`. No trailing slash. It is compiled into the bundle (it is not a secret), so changing it needs a rebuild. |

Render only prompts for `sync: false` values at the first sync. If the real URLs differ from what you typed (a name collision adds a
suffix), correct both in the dashboard and redeploy: the API for `CORS_ORIGINS`, the web app for `VITE_API_URL`.

Never set `FAKE_CLOCK`, `ALLOW_DB_RESET` or `TEST_DATABASE_URL` on Render. Do not copy values from your local `.env`.

## Before you create the Blueprint

1. `render.yaml` must exist on the branch Render syncs. It lives on `deploy/render-prep` until that branch is merged, so either
   merge it or choose that branch when connecting the repository.
2. Confirm CI is green on that commit.
3. Optionally validate the file against Render's published schema (<https://render.com/schema/render.yaml.json>) with any JSON
   Schema validator; this was done once when the file was written.

Creating the Blueprint, connecting the repository and entering the two URLs are manual steps in the Render dashboard.

## Post-deployment smoke tests

Replace `$API` and `$WEB` with the two public URLs.

1. **Health:** `curl -i $API/health` returns `200` with `"database":"up"`. (The first request after a sleep can take about a minute.)
2. **Plans seeded:** `curl $API/plans` lists 4 plans.
3. **Development endpoints are off:** `curl -i -X POST $API/dev/run-renewals` and `curl -i -X POST $API/dev/advance-clock` both return `404`.
4. **CORS is an allow-list:** `curl -i -H "Origin: https://evil.example" $API/plans` has no `Access-Control-Allow-Origin` header, and the same request with `Origin: $WEB` does.
5. **Security headers:** `curl -I $API/health` shows `Cache-Control: no-store` and helmet's headers; `curl -I $WEB` shows `X-Content-Type-Options: nosniff`.
6. **Deep links:** open `$WEB/invoices` directly and reload it; the app loads (it redirects to sign-in when signed out).
7. **Disclosures:** the amber "Demo only: billing is simulated" bar shows on the sign-in, registration and signed-in pages, and the
   registration page warns against reusing a real password.
8. **Core flow:** register, subscribe, upgrade (check proration), schedule a downgrade, pause, resume, cancel, reactivate; use the
   Usage page until the limit blocks; check Billing and History.
9. **Session survives a reload.**
10. **Logs:** the Render log shows no secrets, tokens or stack traces.
11. **Rate limiter sees real clients (see below):** from two different networks, repeated bad logins from one must not block the other.

### Verifying the trusted-proxy setting

`TRUST_PROXY=1` tells Express to trust exactly one proxy hop, the address Render's load balancer appends to `X-Forwarded-For`.
This was tested locally by simulating that header, **not** against Render's real network. After deployment, check it:

1. From network A (for example home Wi-Fi), send repeated failed logins until you get `429 RATE_LIMITED` (the default limit is 20 per
   15 minutes per IP). This locks that network out of sign-in for the window.
2. From network B (for example mobile data), a login attempt must still return `401 INVALID_CREDENTIALS`, not `429`.

If network B is blocked too, clients are being grouped: either the hop count is wrong for Render's current topology or another
proxy (for example a CDN) sits in front. Do not set `TRUST_PROXY=true` (the application rejects it); adjust the hop count only after
confirming how many proxies appear in front. Never trust the leftmost `X-Forwarded-For` entry; a client can set it.

## Free-tier limitations

| Area | Limit (Render docs, 2026-10-29) | Effect on this demo |
|---|---|---|
| Web service sleep | A free web service spins down after 15 minutes without inbound traffic and takes about a minute to wake. | The first visit after a quiet period is slow, and requests may time out while it wakes. |
| Instance hours | 750 free instance hours per workspace per month; all free web services are suspended when they run out. | A second always-on free service in the same workspace shares this pool. |
| Filesystem | Not persistent on free instances. | Nothing in the app writes to disk. |
| Free PostgreSQL | **Expires 30 days after creation**, with a 14-day grace period to upgrade before the database and its data are deleted. | The demo has a fixed lifetime unless upgraded or recreated. |
| Backups | Free databases support **no backups** of any kind. | All data is disposable; do not store anything you cannot lose. |
| Storage | 1 GB. | Ample for a demo. |
| Database count | One free database per workspace. | The Blueprint fails if the workspace already has one. |
| Bandwidth and build minutes | Counted against the plan's included amounts. | Exceeding them can cause extra billing or suspension. |

Free-tier availability and these terms can change; the Blueprint does not guarantee that free resources are available.

### Data lifetime, backup and recovery

There is no recovery path for the free database: when it expires or is deleted, the data is gone. To rebuild, create a new
database, run the Blueprint again (migrations and seeding recreate the schema and plans), and ask users to register again. For
anything you want to keep, upgrade the database to a paid plan that offers backups, and verify a restore yourself.

### Effect of sleeping on the scheduler

Renewals, retries, reconciliation, refund processing and idempotency-key cleanup run from `node-cron` **inside the API process**
(`RUN_JOBS=true`). While the free service is asleep, no job runs. A subscription whose period ended while the service slept stays
without access (access stops exactly at the period end) until the service wakes and the next one-minute cycle renews it. That is
correct but visible: a demo user can see a late renewal. If the service is down for several periods, each missed period is charged
in turn (see [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)). Keeping the service awake with an external pinger is possible but is
against the spirit of the free tier and still burns instance hours.

Because development endpoints are disabled in production, visitors cannot advance the clock or trigger renewals. A demo shows the
subscription, upgrade, downgrade, pause, cancel and usage-limit flows; it does not show a renewal or a failed payment unless you wait
a real billing period.

## Public registration and mock billing

- Billing is **mock-only**. No payment provider is connected, no card data exists anywhere, and no real money moves. The app says so
  on the sign-in, registration and signed-in pages. The brief session-loading and session-unavailable screens do not display it.
- Registration is open to anyone. The database will hold email addresses and bcrypt password hashes from strangers. The registration
  form warns people not to reuse a real password, but treat the data as personal: delete the database when the demo ends.
- There is no email verification, password reset or MFA, and sign-out does not revoke the token (see
  [SECURITY.md](SECURITY.md)). Rate limits are in memory, per process, and reset on every restart or sleep.

## Why this is not a production billing setup

The free plans make this unsuitable for real billing workloads, regardless of the code: the API sleeps (so renewals do not run on
time), the database expires and cannot be backed up, there is no failover, scheduling is in-process, and there is no operator
tooling or alerting for failed refunds. A real deployment needs a real payment provider, an always-on worker, backed-up and monitored
PostgreSQL, a shared rate-limit store, and a fresh security review. See [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).
